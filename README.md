# 讲稿：PROMPTPEEK，共享 KV 的完成顺序

今天要讲的不是又一条越狱提示词。Guanlong Wu、Zheng Zhang、Yao Zhang、Weili Wang、Jianyu Niu、Ye Wu、Yinqian Zhang 在 NDSS 2025 的论文是 *I Know What You Asked: Prompt Leakage via KV-Cache Sharing in Multi-Tenant LLM Serving*，攻击名叫 PROMPTPEEK，DOI [10.14722/ndss.2025.241772](https://dx.doi.org/10.14722/ndss.2025.241772)。他们的测量跑在 SGLang 上，模型是 Llama-2-13B，卡是一张 A100 80GB。

这台机器没有 GPU，也没有 SGLang / vLLM。本地候选模型是 `models/` 里的 Qwen3-4B-Base，量化 Q4_K_M，GGUF，`llama-cpp-python` 0.3.36，CPU，`n_ctx=256`，4 个线程。Qwen 只负责提出下一个 token。调度器是我们写的 radix tree 加最长前缀匹配，不是 SGLang。

## 先把通道说清楚：看的是顺序

多租户服务为了省显存，会让不同用户共用同一段前缀的 KV。前缀上每一个 token 都对上，后面的 KV 才能接着用。SGLang 在此之上用 Longest Prefix Match 排等待队列：和缓存重合得更长的请求先跑。重合长度相同，就保持原来的到达顺序。

攻击者不读别人的张量。他只看自己发出去的请求，谁先完成。论文图 5、图 6 的摆法是：

1. 先发一批完全相同的哑元，数量不少于服务器的 `max_batch`。这批请求先被收进去跑，哑元的 KV 写进缓存。
2. 再发候选。每个候选都是「已经还原的前缀 + 一个不同的下一个 token」。
3. 再发一批相同的后哑元。

命中的时候，那个正确候选和后哑元的匹配长度一样，都比纯前缀多一个 token，而且候选比后哑元先到，于是它夹在两批哑元中间。其余候选匹配更短，排到所有后哑元后面。检测器只认一种图案：恰好一个候选排在后哑元前面。全中、全不中、或者好几个一起提前，都不算唯一命中。

这篇论文的观测是完成顺序。后来的 Auditing Prompt Caching 和 SafeKV 看的是另一位：缓存命中会少算一段 prefill，延迟分布仍然可能露出 1 bit。把调度改成先来先服务，PROMPTPEEK 这条顺序比特没有了，时间差可以还在。报告结尾如果有人问「改成 FCFS 是不是就安全了」，把这两条通道分开答。

## 论文的三个场景，和我们没有重跑的那些比率

论文按攻击者事先知道多少，分了三个场景。下面这三组是他们在 Llama-2-13B、A100 80GB 上、跨 cloze / role / instruction 三个数据集的汇总，写在 Section VI 的总结里。成功率把「完全抽出」和「抽出一段」都算进去，还原比例是抽出的长度除以总长度。这不是我们这次跑出来的数字。

Table II 里 cloze 明显更难：整段 prompt 的成功率 87%、还原比例 64%；role 和 instruction 的成功率是 100%，还原比例分别是 87% 和 93%。PromptBase 上的模板不规则，本地模型经常把下一个 token 放不进候选列表。超过 90% 的 token 用不到 10 次候选请求；平均值仍然可以到几十、上百，因为少数 token 几乎猜不到，而攻击是逐 token 的，卡死一个，后面就断。Table II 的请求数只数候选请求。Table III 把目标换成 Llama-3-8B 的 GQA（8 个 KV head），role 数据集上三个场景都是 100% 成功、100% 还原。论文的解释是 GQA 把每个 token 的 KV 压小了，同样的显存里受害者前缀更不容易被冲掉。

| 场景 | 攻击者事先知道 | 论文平均 SR | 论文平均 RR |
| --- | --- | --- | --- |
| 1 整段 prompt | 什么都不知道 | 95% | 81% |
| 2 恢复 input | 模板已知 | 99% | 99% |
| 3 恢复模板 | 用户填的 input 已知 | 98% | 91% |

场景 2 是他们觉得风险最大的一种：模板往往是公开的，或者同一个应用里大家都在用，秘密只是填进去的那几个词。论文里的 BMI 例子，攻击者大约用 60 次请求就把性别、年龄、体重、身高挖了出来。那个 60 是他们的提示、他们的计数。不要把它和下面我们的 60 当成同一次实验。

## 我们实际还原的场景 2

模板已知，秘密来自很小的字母表，不需要语言模型。

性别。模板是 `性别=`，真实填空是 `男`，字母表是 `{男, 女, 其他}`，一次送出。完成顺序：

```text
前哑元 → 前哑元 → 前哑元 → 前哑元 → 候选[男] → 后哑元 → 后哑元 → 后哑元 → 后哑元 → 候选[女] → 候选[其他]
```

判定 `男`。这一次探测 11 个请求：4 个前哑元、3 个候选、4 个后哑元。

账号后三位。真实秘密 `705`，字母表 `0-9`，每批 4 个候选。还原结果 `705`，停止原因 `recovered`。总请求 60，其中候选请求 20，哑元请求 40。五次探测，每次 4 个前哑元 + 4 个后哑元 + 4 个候选。逐位是：

- 第 1 位 `7`：先试 `[0, 1, 2, 3]` 没有唯一命中，再试 `[4, 5, 6, 7]` 命中。2 轮，24 个请求。
- 第 2 位 `0`：第一批 `[0, 1, 2, 3]` 就命中。1 轮，12 个请求。
- 第 3 位 `5`：同样两轮，`[0, 1, 2, 3]` 然后 `[4, 5, 6, 7]`。2 轮，24 个请求。

已经试过并且没命中的 token 必须从后面的候选里去掉。它们的 KV 已经写进攻击者自己的缓存，再送一次会假装成命中。

## 三条都要在，攻击才走得通

论文 Section VII 把端到端泄露收成三个条件。少一条，这条顺序通道就断。

1. KV 在显存还够的时候一直留着。服务框架倾向于尽量不扔缓存，攻击者才有时间一个 token 一个 token 往下探。
2. 客户端能观察到共享，而且至少能读出 1 bit。PROMPTPEEK 的这一 bit 就是完成顺序。
3. 客户端可以大量、自由地发探测请求，还能用 `max_tokens` 这类参数把单次请求压得很短。

## 同一条探针，防御拆掉的是哪一条

受害者下一个 token 是 `IT`，已知前缀是 `Imagine you are an`，长度 4。候选是 `IT / a / the`。

| 调度 | 提前的候选 | 泄漏 `IT` |
| --- | --- | --- |
| LPM，M=1，论文默认 | 只有 `IT` | 是 |
| 按租户拆开 radix tree，也就是 `cache_salt` 那种隔离 | 没有 | 否 |
| FCFS，不按前缀长度插队 | `IT`、`a`、`the` 三个一起提前 | 否 |
| LPM 分桶 M=2，前缀长度 4，加 1 个 token 不跨桶 | 三个一起提前 | 否 |
| 同一个 M=2，前缀改成 3 | 只有 `an` | 是，边界上仍漏 |
| 真实 token 不在本地候选列表 | 还原 `[]`，原因 `no_unique_hit`，12 个请求 | 否 |
| KV 被驱逐，容量只够放下受害者自己 | 对照实验命中 4；把受害者挤掉之后命中是空 | 否 |

隔离拆的是条件 2 的共享：攻击者的树里根本没有受害者前缀，LPM 无从比较。FCFS 拆的是条件 2 的顺序比特：完成顺序等于到达顺序，检测器看到好几个候选一起提前，拒绝把它当成命中。M=2 在不跨桶的时候削弱的也是这一 bit，缓存其实还共享着，只是差一个 token 不再改变优先级。

M 的实现要说实话。我们用的是 `match_len // M`。前缀长度 4 时，`4 // 2` 和 `5 // 2` 都是 2，多猜对一个 token 不换桶。前缀长度 3 时，`3 // 2 = 1`，`4 // 2 = 2`，多一个 token 仍然换桶，`an` 又被唯一提前。论文 Section VIII 说的缓解是「至少多共享 M 个 token 才升优先级」，他们把这件事留作后续工作。整除分桶不是那个缓解的完整版，边界上会漏。

罕见 token 拆的不是调度，是候选生成。侧信道还在，可是本地列表里没有真值，这一步没有唯一命中，后面的前缀也接不下去。驱逐拆的是条件 1：受害者前缀已经不在树里。

## Qwen3-4B-Base 只负责提候选

论文 Section IV-A1：攻击者在本地放一个和目标共用 tokenizer 的模型，用已经还原的前缀取 top-k 下一个 token，再拿一个最不可能的 token 当哑元。不同模型猜下一个词的能力不一样，那不是他们的重点。我们这里用 Qwen3-4B-Base 的 Q4_K_M，CPU 推理，`n_ctx=256`，4 个线程，不用 GPU。服务器仍然是上面那个 radix / LPM 模型。

三句短句都扣住最后两个 token，看被扣住的第一个 token 在不在 top-8。三句都在，于是按规则用第一句跑侧信道。

| 句子 | 被扣住的后缀 | 首 token 在 top-8 |
| --- | --- | --- |
| The capital of France is Paris. | ` Paris.` | 在 |
| 北京是中国的首都。 | `首都。` | 在 |
| To be or not to be. | ` be.` | 在 |

实际送进调度器的是 `The capital of France is Paris.`。已知前缀 `The capital of France is`，真实后缀 ` Paris.`，侧信道还原 ` Paris.`，逐 token 一致。停止原因 `recovered`。总请求 32：两个 token 各一轮、各 16 个请求（4 个前哑元 + 8 个候选 + 4 个后哑元）。

第一轮送出的候选，按 logit 从高到低，是 ` Paris`、` located`、` ____`、` what`、` ______`、` in`、` __`、`?\n`。真值排在第一，前面那个空格是分词器自己留的。第二轮是 `.`、`,`、`.\n`、`.\n\n`、` and`、换行、两个换行、`?\n`。真值也在这批里。

这只说明：在这句短提示上，4B 基模的 top-8 盖住了被扣住的 token，于是顺序通道能把它读出来。它不是论文 Table II 的 95% / 81%。

SGLang 用 radix tree 加 LRU 存前缀，再用 LPM 排序。vLLM 那一代是 paged attention 上的 block hash，论文写作时共享还没有被做成同样的默认调度。公有云上的 colocation 是作者留的未来工作：请求可能落不到存着受害者 KV 的那张 GPU，共享就不会发生。他们在本地单卡上证明了机制。
